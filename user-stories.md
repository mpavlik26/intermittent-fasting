- I want to create a web application that can be used to manage my Intermittent Fasting.
- It will be created using agile methodology
  - It means the stories will start from the most basic features and will be built incrementally.
  - It's necessary to follow the rules of the user stories not to break any of the existing functionality defined by previous user stories
    - however it's logical some newer stories will change the behaviour of the previous ones
      - it will be great if you identify those conflicts and explicitly address them for being able to resolve them correctly
  - Slices are moved to `user-stories-archive.md` only once a following slice exists to prove them finished — a slice is never split across the live file and the archive. The current (most recent) slice always stays here until a new one begins.
- The ninth slice will have the following background and user stories:
  - Background:
    - Now that bonus minutes (US-18) can be moved into personal storage and accumulate there over time, the raw minute counts shown around the app can grow into the hundreds or thousands, which is hard to read at a glance
  - User stories:
    - US-19:
      - As the user, whenever any badge or the bonus storage display would show 60 or more minutes, I want it shown as a combination of hours and minutes instead of a large raw minute count, so it's easier to read at a glance
        - Below 60 minutes, the display is unchanged - still a raw minute count (e.g. "+45m")
        - At 60 minutes or more, the display switches to the "Xh Ym" format (e.g. "+1h 5m"), omitting the minutes part when it's an exact multiple of 60 (e.g. "+2h", not "+2h 0m")
        - This applies to every place a bonus/penalty minute amount is shown: the fasting/eating bonus badge, the penalty badge, the "prolonging"/"premature start" break-fast penalty amounts, the stored-bonus indicator in the header, the live slider value in the "Move Bonus to Storage"/"Use Stored Bonus" dialog, and the Reward/Penalty tags in the History section
        - Countdown/duration displays that already use the "HH:MM:SS" clock format (e.g. the main countdown timer) are unaffected - this story only concerns discrete minute amounts shown as "+Nm"/"-Nm"
- The tenth slice will have the following background and user stories:
  - Background:
    - Today, Fasting bonus and Eating bonus are tracked separately but merge into a single combined stored-bonus pool, both bonus calculations are halved ("bonus divisor"), and the two break-fast penalties are handled inconsistently (one applied immediately, one deferred) and displayed as a single combined penalty. As the app matures, a stricter separation is needed: Fasting and Eating should each have their own independent bonus, penalty, and storage pool, with each only ever affecting its own kind of window, and no halving - so the rules are easier to reason about and to display accurately
  - User stories:
    - US-20:
      - As the user, I want Fasting bonus and Eating bonus to become two fully separate, non-interchangeable bonuses, each applied only to its own kind of window, instead of today's single combined bonus logic
        - Eating bonus is applied by extending the nearest upcoming Eating window
        - Fasting bonus is applied by shortening the nearest upcoming Fasting window
          - if this would reduce that Fasting window's length to zero or below, that Fasting window (and its following Potential Eating window) is skipped entirely, and the next Eating window begins immediately after the current one ends
            - the Fasting bonus is reduced by the standard 16-hour Fasting duration for each window skipped this way
            - this can repeat multiple times in a row (several Fasting/Potential-Eating window pairs skipped back to back) if the Fasting bonus is large enough
            - this skipping must not wait until the current Eating window actually ends to happen - it must be resolved immediately/eagerly: the current Eating window is immediately extended by a further standard 8 hours (once per skip) while the remaining Fasting bonus is immediately reduced by the standard 16-hour Fasting duration (once per skip), so the user always sees right away how long their current Eating window and the eventual next Fasting window will really be, rather than discovering it only once the original Eating window ends
        - if the user ends an Eating window early (logs the last meal before the window's end), the entire remaining time is credited to the Eating bonus (not half of it, as today)
        - if the user starts eating later than the earliest possible moment (i.e. later than the start of the Potential Eating window), the entire extra time is credited to the Fasting bonus (not half of it, as today)
        - the halving ("bonus divisor") used today for both of these bonus calculations is removed entirely - both bonuses are now full 1:1. This does not affect the existing penalty multipliers (see below), which are unchanged by this story
      - As the user, I want Fasting penalty and Eating penalty to become two fully separate, independent penalties (effectively negative bonuses of their own kind), which can both be pending/active at the same time
        - the user incurs a penalty the same way as today, by breaking an active Fasting window early and choosing one of the two existing options:
          - prolonging the Eating window that just ended: as today, this restarts the Fasting window immediately from the actual (prolonged) last-meal time, discarding any Eating bonus already banked from the Eating window's earlier natural end - the only change is that the penalty (double the time by which the previous Eating window was prolonged) is no longer applied immediately to extend this restarted Fasting window; instead it creates/adds to a new Eating penalty, deferred to the nearest upcoming Eating window - like the premature-start case below
          - starting the next Eating window prematurely: as today, this creates/adds to a Fasting penalty equal to double the time between the premature start and the original Fasting window's end - this penalty was and remains deferred
        - both penalties are applied to the nearest upcoming window of their own matching kind:
          - Fasting penalty extends the nearest upcoming Fasting window
          - Eating penalty shortens the nearest upcoming Eating window
            - if this would reduce that Eating window's length to zero or below, that Eating window is skipped entirely (the cycle continues straight into the next Fasting window), the Eating penalty is reduced by the standard 8-hour Eating duration for each window skipped this way, and the remainder is applied to the following Eating window - this can cascade exactly like the Fasting-bonus skipping case above
            - just like the Fasting-bonus case, this must be resolved immediately/eagerly - repeatedly skipping a full standard 8-hour Eating window and reducing the Eating penalty by 8 hours each time, until it drops below 8 hours - so the user immediately sees the full length of the resulting long Fasting window, rather than discovering the skip only once they reach the point where the skipped Eating window would have started
      - As the user, I want the existing stored-bonus mechanism (US-18/US-18.1) to keep working under the new model, but with two fully separate storage pools instead of one
        - there are now two independent storage pools: stored Fasting bonus and stored Eating bonus
        - moving a bonus into storage ("Move Bonus to Storage") always keys by the type of the bonus being stored, not by which window the user is currently in - storing Fasting bonus always draws from the current Fasting bonus (regardless of current window), and storing Eating bonus always draws from the current Eating bonus
        - using a stored bonus ("Use Stored Bonus") always applies it back to the matching bonus type - stored Fasting bonus can only ever shorten a Fasting window, stored Eating bonus can only ever extend an Eating window
        - reserving use of a stored bonus while inside the "wrong" window, so it can be applied safely once the matching window starts (today: reserving stored bonus during Potential Eating, applied once the next Eating window starts), is extended symmetrically: it must also be possible to reserve use of stored Fasting bonus while inside an Eating window, to be applied once the next Fasting window starts
      - As the user, I want the Windows History (US-10) to keep recording only what I actually experienced
        - windows that get fully skipped/cascaded away by a large bonus or penalty (per the eager-skip rules above) before the user ever sees them as a live, current window are not recorded as separate History entries
        - only the final, surviving window that the user actually lived through is recorded, together with whichever bonus/penalty amounts ended up applied to it
      - As the user, I want the UI to clearly distinguish all four of these values everywhere they're shown, instead of today's combined Bonus/Penalty badges
        - the single combined bonus badge and single combined penalty badge are replaced with up to four separate badges/indicators as relevant to the current window: Fasting bonus, Eating bonus, Fasting penalty, Eating penalty
        - the single combined stored-bonus indicator in the header is replaced with two separate indicators, one for stored Fasting bonus and one for stored Eating bonus
        - the "Move Bonus to Storage"/"Use Stored Bonus" dialogs, their sliders, and the Reward/Penalty tags in History all follow the same Fasting/Eating split
        - the minute-formatting rules from US-19 ("+Nm" below 60 minutes, "Xh Ym" at 60 minutes or more) continue to apply identically to every one of these new/split badges, indicators, dialog values and History tags
      - This story changes the behaviour of several previous stories - the following conflicts are identified and resolved as described above:
        - US-3 (fasting bonus from continued fasting) and US-4 (eating bonus from early finish): the "bonus divisor" halving is removed for both (now full 1:1); both bonuses can now cascade across/skip multiple windows instead of only ever applying to a single next window
        - US-7 (break-fast penalties): "prolonging" still immediately restarts the Fasting window (as today), discarding any already-banked Eating bonus from that window's earlier natural end (as today) - the only change is that its penalty is no longer applied immediately to extend that restarted Fasting window; it's deferred to the next Eating window as the new Eating penalty, matching how "premature start" already deferred its penalty (now the Fasting penalty) to the next Fasting window
        - US-10 (history): unaffected in spirit, but now explicitly only records windows actually experienced by the user, never a skipped/cascaded intermediate window
        - US-15 (retrospective log landing inside an active fast): continues to reuse the (now-restructured) break-fast handlers above, with no behavioural change beyond what US-7's restructuring already implies
        - US-17 (penalty multiplier halving): the existing ×2 multipliers for both penalties are unchanged by this story
        - US-18/US-18.1 (stored bonus): the single combined storage pool and single pending-use reservation are replaced by two independent pools and two independent reservations, as described above
      - Testing scenario (worked example, demonstrating the eager Fasting-bonus-skip cascade):
        - the user is in an Eating window running from 8:00 to 17:00 (a standard 8-hour window plus a 1-hour Eating bonus already applied) and has 20 hours of Fasting bonus available
        - rather than waiting until 17:00 (the window's end) to discover the Fasting bonus would wipe out the next Fasting window, the app immediately and eagerly extends the current Eating window by a further standard 8 hours (new end: 1:00 the next day) and reduces the available Fasting bonus by the standard 16-hour Fasting duration, leaving 4 hours of Fasting bonus
        - if the user then genuinely finishes eating at 1:00, the following Fasting window is shortened by the remaining 4-hour Fasting bonus, giving a 12-hour Fasting window, from 1:00 to 13:00 the next day
        - if the available Fasting bonus had instead been large enough to exceed multiple 16-hour multiples, the same 8-hour eager-extension/16-hour-bonus-reduction step would repeat as many times as needed until the remaining Fasting bonus drops below 16 hours, at which point it applies normally to the next real Fasting window
      - Testing scenario (worked example, demonstrating prolonging discarding a banked Eating bonus and deferring the Eating penalty):
        - the user is in an Eating window running from 8:00 to 17:00 (standard 8 hours plus a 1-hour Eating bonus already applied) and has 3 hours of Fasting bonus available
        - the user logs their last meal at 12:00; since that's before the window's 17:00 end, the Eating window continues as normal until 17:00, at which point the app transitions to Fasting and banks a 5-hour Eating bonus (the remaining time between 12:00 and 17:00) for the next Eating window
        - at 18:00, while already inside this Fasting window, the user logs that they actually kept eating until 18:00: this prolongs the Eating window that ended at 17:00, so the app restarts the Fasting window from 18:00 (discarding the 5-hour Eating bonus just banked, since the user didn't really stop eating at 12:00 after all) and creates a 2-hour Eating penalty (double the 1-hour overshoot past 17:00), deferred to the next Eating window
        - the restarted Fasting window (18:00 to 7:00 the next day, 13 hours) is shortened only by the still-untouched 3-hour Fasting bonus - the new 2-hour Eating penalty does not affect it
        - the user starts eating at 8:00 (1 hour after the 7:00 Potential Eating window began), earning a fresh 1-hour Fasting bonus for the next Fasting window; this Eating window is a standard 8 hours shortened by the pending 2-hour Eating penalty, giving a 6-hour window from 8:00 to 14:00
        - the user finishes eating early at 12:00, so when the app transitions to Fasting at 14:00 it banks a fresh 2-hour Eating bonus for the next Eating window, and the new Fasting window (from 12:00, 16 hours shortened by the 1-hour Fasting bonus just earned, i.e. 15 hours) runs until 3:00 the next day
    - US-21:
      - As the user, I want to explicitly end my current Eating window instead of waiting for its end, so that when I know I will not eat anymore (typically in a long Eating window stretched by accumulated Eating bonus) the app immediately shows me as fasting
        - the action is available only during an Eating window and is independent of logging the last meal
        - its button is deliberately low-key (small, secondary style) - clearly less prominent than the Log Last Meal button, so it is not pressed by accident
        - pressing it opens a dialog (instead of hold-to-confirm; the dialog is the safeguard) that states when the Eating window originally ends (E, rendered via `renderTime`) and offers 4 choices:
          - "Last meal is now" - confirmed immediately by the click
          - "Last logged meal at HH:MM" - offered only if a last meal has already been logged in this Eating window; the time is shown explicitly (via `renderTime`); confirmed immediately by the click
          - "Different time" - reveals a time field and a Confirm button; the allowed range is from the already logged last meal (or from the Eating window start if none is logged) up to now; it behaves exactly as if the user had logged the last meal at that time (US-15) and then explicitly ended the Eating window
          - "Cancel" - closes the dialog and leaves the Eating window as it is, which keeps running until E
        - choosing "now" or "different time" while a last meal is already logged overwrites it with the chosen time, which therefore can never be earlier than the logged last meal
        - from that moment the app behaves as if the Eating window had expired normally:
          - the Fasting window starts at the chosen last meal time T (the Fasting start is therefore never the moment of the press unless the user chose "now")
          - the Eating bonus is banked as (original Eating window end E - T), as for an early finish (US-4/US-20)
          - if T is so far in the past that the resulting Fasting window has already ended, the app fast-forwards as it does for any expired window
          - the Fasting bonus/penalty and stored-bonus reservations are applied to the new Fasting window exactly as in a normal transition
          - the Windows History (US-10) records the Eating window as today, with its original planned end E
      - As the user, I want a clear way back to eating if I change my mind after explicitly ending the Eating window
        - while the resulting Fasting window runs and the current time is before E, the app explains how to do it, e.g. "You ended your Eating window early. Until HH:MM you can resume eating without penalty: open 'Break Fast Prematurely' and choose 'Option 1: Prolong Eating' ('Prolong & Start Fast')." (the time is rendered via `renderTime`)
        - before E, the Break Fast dialog offers only Prolong Eating (no Premature Start), because the user is still within the bounds of the original Eating window
          - there is no penalty; the Fasting window restarts from the prolonging time t; the Eating bonus is recalculated as E - t (the bonus banked by the explicit end is discarded)
          - the dialog shows a 0m penalty and the recalculated Eating bonus
        - at or after E, everything works exactly as if the Eating window had not been explicitly ended (US-7): Prolong Eating creates an Eating penalty of double the overshoot past E, deferred to the next Eating window, and discards the banked Eating bonus; Premature Start is offered as today
        - US-15 retrospective logs landing inside such a Fasting window follow the same rule by their time: before E a penalty-free prolong, at or after E the existing penalty logic
      - This story changes the behaviour of several previous stories - the following conflicts are identified and resolved as described above:
        - US-7 (break-fast penalties): before the original Eating window end E of an explicitly ended Eating window, only Prolong Eating is offered, penalty-free, with the Eating bonus recalculated instead of discarded; from E on, unchanged
        - US-4/US-20 (Eating bonus): an explicit end becomes another way of banking an Eating bonus, with the same E - Fasting start formula
        - US-14 (hold-to-confirm): not used for the explicit-end action; its confirmation is the choice in the dialog, and the Log First/Last Meal buttons keep hold-to-confirm unchanged
        - US-15 (retrospective log): the "different time" choice reuses the same last-meal logging as the retrospective log in an Eating window
        - US-15 (retrospective log inside an active fast): reuses the restructured prolong handler, so its result depends on whether the logged time is before or at/after E
      - Testing scenario (worked example):
        - the user is in an Eating window running from 8:00 to 17:00 (E = 17:00) and at 12:00 presses the explicit-end button; the dialog shows that the window ends at 17:00 and, with no last meal logged, offers only "now", "different time" and "cancel"
          - "cancel": nothing changes, the Eating window keeps running until 17:00
          - "now": the Fasting window starts at 12:00, a 5-hour Eating bonus is banked (17:00 - 12:00) and the History records the Eating window 8:00-17:00
          - "different time" 10:00: the Fasting window starts at 10:00 and a 7-hour Eating bonus is banked (17:00 - 10:00)
          - if the user had logged the last meal at 11:20, the dialog additionally offers "Last logged meal at 11:20" and choosing it starts Fasting at 11:20 with a 5h40m Eating bonus; the "different time" range is then 11:20-12:00
        - continuing with the "now" variant:
        - at 15:00 the user opens Break Fast Prematurely and chooses Prolong Eating: no penalty, the Fasting window restarts from 15:00, and the Eating bonus is recalculated to 2 hours (17:00 - 15:00)
        - alternatively, if the user only chooses Prolong Eating at 19:00, it works as before the explicit end: a 4-hour Eating penalty (double the 2-hour overshoot past 17:00) is deferred to the next Eating window, the Fasting window restarts from 19:00 and the banked Eating bonus is discarded
